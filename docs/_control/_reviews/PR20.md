## 阻断项
- **X1 B4 dev artifact 不是由代码生成的，receipt 验不上**
  - 证据：把提交版 `artifacts/s2/b4-dev.json` 中的 `llm_calls`（顶层、每个 episode、metrics 里 B4_STRICT）全部改为 0 并去掉 `canonical_replay_live_llm_calls`，其余内容与断网回放的输出逐字相同，哈希为 `b49a6c0cc8ad15c25866b89f5eea04956e615afca8ae753fcab8df4f9017e971`。
  - 但提交版的 `receipt_sha256 = ad473c0f…f238` 按 `b4_dev.py` 的哈希规则（排除 runtime_versions），无论是否包含那个新增键都**无法复现**；而 `canonical_replay_live_llm_calls` 这个键在 src 和 scripts 里都找不到出处。
  - 后果：报告和 artifact 里 receipt 这个数字无法核验。按指南书 PB-P0-02-B，验不了的 receipt 不能作为证据。
  - 修复：实际联网调用次数改由代码写入一个**不进入 receipt 哈希**的字段（类似 runtime_versions），或者写入单独的调用台账文件；artifact 必须由提交的代码一次生成，receipt 能复算。不需要新的 NIM 调用。

## 需要在同一次修复中改正（§1 偏差，实测对本次结果影响为 0）
- **X2 D4 的回落条件没有实现"遇到 fault ID 或未知 ID → 回落"**
  - 现在的实现会跳过排在前面的 fault ID，继续选后面通过验证的结构；未知 ID 只记录下来，不会触发回落（`episode.py:533-537`）。D4 原文要求"遇到 fault ID、未知 ID、空结果、error、超时、ReplayCacheMiss → 回落 strict"。
  - 实测：33 seed × 4 变体中，27 个 TEXT_TIEBREAK 决策里"被选结构之前排着 fault ID"0 次、"proposal 含未知 ID"0 次、"被选的不是第一名"0 次；有效 proposal 里第一名是 fault ID 的也是 0 次。所以改正后本次 decisions 应该不变。
  - 修复：按顺序扫描 proposal，先遇到 fault ID 就回落为 `TIEBREAK_FALLBACK:FAULT_ID`；只要含未知 ID 就回落为 `TIEBREAK_FALLBACK:UNKNOWN_ID`。补对应测试。

## 非阻断项
- **N1 B4 结果主要被模型输出格式失败主导（D4 下结论前必须说明）**：386 个缓存响应中，只有 71 个能解析出 `items`；310 个是结构损坏的 JSON（例如 `{": [{": "The drive motor was serviced…`），5 个被截断（`finish_reason=length`）。因此 tiebreak 绝大多数回落为 INVALID_PROPOSAL，各变体的差异不能解读为"文本上下文的效果"。改 prompt 或 schema 会改变缓存键，需要重新调用 NIM，应单独出卡并由用户决定预算。
- **N2 跨 worktree 依赖**：`scripts/l6_b4_meterless_replay.py:39` 在找不到 vendored Meterless 时，会回退到 `ROOT.parent / "l5a-hygiene"`。合并卡会删掉 l5a worktree，之后 B-4 就无法复现。应改为初始化 submodule，或者明确报错。
- **N3 授权计数差 1**：报告写"27 次 TEXT_TIEBREAK，其中 26 次产生授权"，本审查按 decisions 统计为 25 次。请在修复报告里说明口径。
- **N4 B-5 的 B1/B2 行**：可以用 `score_against_b1_denominators` 在同一子集上算出 B1，现在全部标为 n/a，可比性不足。
- **N5 在线回落原因**：回放中 ReplayCacheMiss 会被 adapter 当作 `FileNotFoundError` 捕获并记为 PROVIDER_ERROR，和真实的 provider 错误混在一起。建议单独记一个原因。
