## 非阻断项（建议放进后续卡）
- **N1 artifact 膨胀，哈希变化原因写得不全**：`b3_dev.py` 为了 A3 审计，把首 20 seed 的 decisions 嵌进 `b3-dev.json`，文件从 0.36 MB 增长到 4.6 MB，而且这部分进入了 receipt 哈希。报告只把哈希变化归因于 `structure_id`，漏了这一条。建议后续把审计用的 decisions 拆到单独文件，或者明确保留并在 A04 中说明。
- **N2 L3 receipt 的来源标注过期**：`scripts/l3_equivalence.py:154` 把 `base_git_sha` 写死成 `2a3b52d…`（这是本 PR 之前就有的写法）。结果是，用 ab509d3 代码重新生成的 `zetaris-equivalence.json` 仍然声称自己基于 2a3b52d。建议改为运行时 `git rev-parse HEAD`。
- **N3 D7 关联方式**：诊断值挂在"同一 target 最近一条诊断行"上；该 target 没有诊断行时，这两个值会被直接丢弃，不报错。这次 130 seed 的指标没有受影响，但建议加一个计数断言，或者在 trace 里写入 command_id。
- **N4 锁存在空证据时会跳过（不是 fail-closed）**：`episode.py` 的 `latch_from_faults` 新增了 `if not supporting_ids and fault in {STUCK, BELT}: continue`；窗口缺失时退回完整的 `evidence_ids`，不再是原来的 `[-4:]`。生产路径下 `check_faults` 一定会给出窗口，这个分支走不到；130 seed 行为也与旧版一致。但从安全语义看，建议改回"证据为空照样锁存"，并补一个测试。
- **N5 D9 删除前断言无法复核**：PR 只有一个压缩后的提交，看不到"删除前先确认锁存先执行"的过程。新测试是对整个 episode 打 `run_b3` 桩，只覆盖 OBJECT_MISSING 一个场景。替代证据是本审查做的 130 seed 与 d54faa7 的行为等价比对（见 A3 一行），我认为足够。
- **N6 卡面勘误（卡的责任，不是 PR 的）**：A2 引用的 `artifacts/h1/b1-corrected-dev.json` 里没有逐 seed 哈希，应改为以 d54faa7 版 `b3-dev.json` 中的逐 seed B1 哈希为基准；P5 的 `faults.py` 实际路径是 `src/rra/s2/faults.py`。
