## 阻断项
- **X1 eval 守卫会挡住 B4 的续跑和 live 之后的 replay 生成**（A06 §3.3 "may be resumed"、§3.4 "generated afterwards in replay mode … twice"）。
  - `_validate_eval_guard`（`final_v3.py:123-135`）要求：工作区干净；`git diff --name-only <tag> HEAD` 中只能出现 `config/eval_seeds_v3.json` 和 `artifacts/eval_v3/`。
  - 但 B4 live 会把响应写进 `artifacts/llm_cache/`（`b4_dev.py:196`）。后果有两个：
    - (a) live 中断后，`llm_cache` 下已有未跟踪的新文件，工作区不干净，无法续跑；
    - (b) live 完成并提交缓存后，`<tag>..HEAD` 中出现 `artifacts/llm_cache/*`，后面的两次 replay 生成被拒绝。
  - 次要后果：每跑完一个 row，都要先提交它的输出，才能跑下一个 row，否则工作区不干净。
  - 要求：守卫的实质是"冻结之后 `src/` 以及其余实现文件没有改动"（A06 §2.3）。改为：已跟踪的改动（`<tag>..HEAD` 与工作区）和未跟踪文件，都必须属于白名单 {`config/eval_seeds_v3.json`、`artifacts/eval_v3/**`、`artifacts/llm_cache/**`}，不再要求工作区完全干净。`artifacts/llm_cache/**` 只允许**新增**文件，修改或删除已有缓存文件都拒绝。补测试：缓存目录有未跟踪文件时可以续跑；`<tag>` 之后提交了缓存时仍可以 replay；`src/` 有改动时拒绝；修改已有缓存文件时拒绝。
- **X2 续跑时，已经发生的 live 请求数可能丢失，上限因此失效**（A06 §3.3 上限 2,500，§5 停止条件）。
  - `_prior_distinct_live_requests` 只读取 `b4.json`，而 `b4.json` 只在 `run_row` 正常结束时写出。如果中途崩溃、Ctrl-C，或者 401/403 抛出 `SystemExit`，本次已发生的 live 请求数不会留下记录，续跑时 `already` 从 0 重新计起。
  - 要求：在每次 live 调用**之前**，把请求 sha256 追加写入一个只增不减的账本（例如 `artifacts/eval_v3/live_ledger.jsonl`，一行一个 sha，不写请求内容）；`already` = 账本中不同 sha 的个数。补测试：模拟中途异常后续跑，计数从账本接上，并且在上限处停止。
